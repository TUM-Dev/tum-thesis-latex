\chapter{Introduction}\label{chapter:introduction}

% Motivation
Fuzzing is a testing technique that repeatedly executes a program with automatically generated inputs to search for bugs, in particular security vulnerabilities.
It has become widely adopted in recent years, for example, through OSS-Fuzz, a service by Google that continuously fuzzes open-source projects~\cite{serebryanyOSSFuzzGooglesContinuous2017}.
In its first five years of operation, OSS-Fuzz exposed more than \num{49000} bugs~\cite{kimBugOssBenchmarkRealworld2024}.

Notably, the majority of bugs found this way were not present from the start: four in five were introduced by code changes, known as regressions~\cite{zhuRegressionGreyboxFuzzing2021b}.
Such regressions are best caught before a change reaches production, for instance, as part of a \ac{ci-cd} pipeline, where fuzzing time is limited.
Consequently, recent work has focused on adapting the fuzzing process to be practical in such environments, both by improving how fuzzers explore modified code and by preparing the inputs they start with~\cite{j.wolffShiftingFuzzingLeft2025, LargeScaleEmpiricalAnalysis}.

\section{Problem Statement}
The latter is particularly important because most practical fuzzers, such as AFL++\cite{fioraldiAFLCombiningIncremental2020}, are mutation-based: they take a set of existing inputs, the seed corpus, and mutate them to explore new program behavior.
Without suitable seeds, such fuzzers rarely reach deep program logic, since valid input structures are unlikely to arise from random mutation alone.
The seed corpus, therefore, gives the fuzzer its head start, and its quality has a significant impact on fuzzing results~\cite{klees2018}.
In particular, minimizing a large corpus to a small set of seeds that preserves its coverage, known as corpus distillation, improves fuzzing effectiveness~\cite{herreraCorpusDistillationEffective2020, herreraSeedSelectionSuccessful2021}.
Likewise, selecting seeds that target the code of interest helps the fuzzer reach it more quickly~\cite {yooImprovingConfigurabilityUnitlevel2021, kimBugOssBenchmarkRealworld2024, canakciTargetFuzzUsingDARTs2022}.

Mutation-based fuzzers, however, assume that such a corpus already exists.
In practice, seeds must first be created by someone or something, and existing corpora may lack the input structures needed to reach the changed code.
Related work has therefore explored generating seeds from scratch, most recently using \acp{LLM}~\cite{liuEvaluatingLLMBasedRegression2026}.
These approaches consider only the changed code itself, although many bugs manifest in code that is merely affected by the change~\cite{zotero-item-324}.
Moreover, they ignore that in commit-based fuzzing, the same project is fuzzed repeatedly, so an existing corpus is often available and can be highly valuable.

\section{Proposed Solution}
This thesis proposes TACCO (Targeted Affected-Code Corpus Optimization), a pipeline that improves the seed corpus before fuzzing starts, giving the fuzzer a head start on regressions in time-limited scenarios.
The approach builds on the \ac{CoI}-Fuzzer, an existing tool by Hundsdorfer~\cite{zotero-item-324}, to first identify code that is transitively affected by a commit.
If a corpus exists, it is heuristically distilled to the seeds most relevant to that code.
An \ac{LLM} agent then uses its semantic understanding of the code, which a fuzzer lacks, to generate additional seeds that cover affected code the corpus does not yet reach.
The two techniques thus complement each other: the \ac{LLM} provides well-formed inputs with the structure needed to reach the affected code, while the fuzzer mutates them into the malformed variants that ultimately trigger the crash.

\section{Results}
The approach was evaluated in two empirical studies on real-world regressions from the BugOSS benchmark~\cite{kimBugOssBenchmarkRealworld2024}.

The first study determined the optimal pipeline configuration across six projects.
Starting from the distilled corpus increased coverage of affected code over the project's own corpus by up to \SI{52.3}{pp} on five of six projects, with a slight decrease of \SI{2.2}{pp} on the sixth, while producing corpora \SIrange{42}{98}{\percent} smaller.
Bounding the affected code to the vicinity of the change site proved unsafe, as it excluded the crash site in two of six projects and reduced coverage of the full affected region by a median of \SI{9.7}{pp}.

The second study compared this corpus against the corpus shipped with each project in AFL++ campaigns on twelve projects.
While the pipeline did not change how often regressions were found, it shortened the median expected time to exposure by \SI{71}{\minute}, or \SI{31}{\minute} including augmentation time, although this trend is not statistically significant.
The differences are attributed to two factors: distillation focuses the fuzzing budget on relevant seeds but can discard seeds that closely resemble the required input, whereas augmentation adds input structures that the original corpus lacked and partly compensates for such losses.

\section{Contributions}
To summarize, this thesis makes the following contributions:
\begin{itemize}
    \item TACCO, a pipeline that combines corpus distillation and \ac{LLM}-based seed generation to target the code affected by a commit,
    \item a tool that distills a given corpus to a minimal set of seeds covering the code affected by a commit,
    \item an \ac{LLM} agent that generates targeted seeds to augment any given corpus, increasing coverage of the affected code,
    \item an empirical study of how the starting corpus and the target scope affect the generated corpus, and
    \item an empirical study comparing the fuzzing effectiveness of AFL++ with the original and the distilled and augmented corpus, including an analysis of the factors behind the observed differences.
\end{itemize}
